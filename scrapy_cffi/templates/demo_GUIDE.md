# Demo project

Generated by `scrapy-cffi demo`. Remove an existing `demo/` directory before generating it again.

## Variants

| Command | Scheduler / ingress |
| --- | --- |
| `scrapy-cffi demo` | In-memory scheduler |
| `scrapy-cffi demo -r` | Redis scheduler / Redis ingress |
| `scrapy-cffi demo -m` | RabbitMQ request queue with Redis dedup/session state |
| `scrapy-cffi demo -k` | Kafka start/work request topics with Redis dedup/session state |

Every generated Demo includes project-local Docker managers. The same commands
work from Windows or Linux/macOS:

```bash
# Windows
docker-demo.bat verify single
docker-demo.bat verify sentinel
docker-demo.bat verify cluster
docker-demo.bat verify-all
docker-demo.bat verify-interrupt single
docker-demo.bat verify-interrupt-all

# Linux/macOS
./docker-demo.sh verify single
./docker-demo.sh verify sentinel
./docker-demo.sh verify cluster
./docker-demo.sh verify-all
./docker-demo.sh verify-interrupt single
./docker-demo.sh verify-interrupt-all
```

`verify` starts the selected infrastructure and both Demo servers, seeds the
start request, executes a real incremental crawl, then removes that topology's
containers and volumes. Framework, crawler-console, server, enqueue, and
PASS/FAIL logs remain under `artifacts/demo-verification/<topology>/`.
`verify-all` runs the supported topologies serially. Memory Demo runs only the
single case because it has no infrastructure.
`verify-interrupt` sends a real console interrupt to `runner.py`, waits for its
graceful shutdown, and verifies non-persistent Redis keys, RabbitMQ queues, or
Kafka topics were removed. On Windows it uses a new process group plus
`CTRL_BREAK_EVENT`; interactive Ctrl+C and Ctrl+Break share the same shutdown
event.

Kafka takes precedence when `-k` is combined with another broker flag.

## Local infrastructure

All topology templates are generated automatically. They can also be managed
without running the crawler:

```bash
./docker-demo.sh plan cluster
./docker-demo.sh up cluster
./docker-demo.sh status cluster
./docker-demo.sh reset cluster
./docker-demo.sh down cluster
```

For RabbitMQ/Kafka, `sentinel` means a single broker plus Redis Sentinel;
`cluster` means the three-node broker cluster plus Redis Cluster. This preserves
distributed Redis deduplication for both MQ schedulers.

Production does not use these Compose stacks. Only the crawler application is containerized and it connects directly to real database/MQ machines.

## Run

Start the mock HTTP/WebSocket server under `demo_server`, then:

```bash
cd demo
python runner.py
```

The generated runner imports its default Spider class directly. `python
runner.py` runs every generated spider; `runner.main()` runs
`runner.DEFAULT_SPIDER`. Generated settings also use imported classes rather
than opaque strings, so IDE navigation and completion work without manual
configuration.

Redis ingress:

```bash
redis-cli RPUSH customRedisSpider_test "http://127.0.0.1:8002"
```

RabbitMQ (`demo -m`) generates `push_rabbitmq_demo.py`:

```bash
python push_rabbitmq_demo.py
```

Kafka start requests go to the generated spider's `kafka_start_topic`; follow-up requests use its separate `kafka_topic`.

## Persistence

- Redis/RabbitMQ/Kafka demos default to `SCHEDULER_PERSIST=False`. RabbitMQ and
  Kafka still require Redis for distributed deduplication; normal exit and
  Ctrl+C remove their request transport plus Redis dedup/session state.
- RabbitMQ/Kafka persistence retains Redis dedup/session state when enabled.
- Ctrl+C follows the same graceful persistence path as normal shutdown.
- RabbitMQ queues use stable durable declarations in both modes; persistence
  controls message delivery and shutdown deletion, avoiding declaration
  conflicts between `push_rabbitmq_demo.py` and the crawler.

See [MQ and local infra](https://github.com/aFunnyStrange/scrapy_cffi/blob/main/docs/usage/11-mq.md) and [deduplication](https://github.com/aFunnyStrange/scrapy_cffi/blob/main/docs/usage/15-deduplication.md).
