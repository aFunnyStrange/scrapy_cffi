# Request queue architecture

Redis, RabbitMQ, and Kafka are parallel infrastructure capabilities:

```text
infra/redis
infra/rabbitmq
infra/kafka
```

There is intentionally no `infra/broker` parent. Redis lists and Streams can also act as brokers, so infrastructure is grouped by concrete external system rather than by a misleading product category.

Schedulers consume stable capabilities from `scrapy_cffi.repo.contracts`:

- `RedisRepositoryProtocol` for distributed deduplication, session state, Redis queues, and Redis Stream ingress;
- `RequestQueueRepositoryProtocol` for request publication, leasing, acknowledgement, size, and transient cleanup.

RabbitMQ and Kafka implementations live in `scrapy_cffi.repo.queue`. Retry and client replacement are provided by `ResourceService`, not by either infra client.

## Installation

```bash
pip install "scrapy_cffi[rabbitmq]"
pip install "scrapy_cffi[kafka]"
```

## RabbitMQ scheduler

RabbitMQ carries start and incremental request objects. Redis remains required for distributed deduplication and optional persistent Cookie/session state.

```python
from scrapy_cffi.config import RabbitMQInfo, RedisInfo
from scrapy_cffi.scheduler import RabbitMqScheduler

settings.REDIS_INFO = RedisInfo(URL="redis://127.0.0.1:6379/0")
settings.RABBITMQ_INFO = RabbitMQInfo(
    URL="amqp://guest:guest@127.0.0.1:5672/"
)
settings.SCHEDULER = RabbitMqScheduler
```

Queue declarations remain `durable=True` and `auto_delete=False` so persistent and transient crawlers may share their identity. `SCHEDULER_PERSIST=False` uses transient messages and deletes framework-owned start/work queues on normal exit and Ctrl+C.

The infra client uses one-shot `aio_pika.connect`; framework retry and node replacement happen only in the service layer.

## Kafka scheduler

Kafka uses separate start/work topics and manual contiguous offset commits:

```python
from scrapy_cffi.config import KafkaInfo, RedisInfo

settings.REDIS_INFO = RedisInfo(URL="redis://127.0.0.1:6379/0")
settings.KAFKA_INFO = KafkaInfo(URL="127.0.0.1:9092")
```

`QueueMessage` is the stable repository delivery model. Scheduler code does not import aiokafka records or the concrete Kafka client.

## Direct publication

```python
resources = build_resource_service(settings, asyncio.Event())
await resources.start()
try:
    if resources.rabbitmq is None or resources.kafka is None:
        raise RuntimeError("RabbitMQ and Kafka must be configured")
    await resources.rabbitmq.push("start_queue", b"https://example.com")
    await resources.kafka.push("start_topic", b"https://example.com")
finally:
    await resources.close()
```

`scrapy-cffi demo -m` and `scrapy-cffi demo -k` also generate directly
runnable publishers under `scripts/`:

```bash
python scripts/push_rabbitmq_demo.py
python scripts/push_kafka_demo.py
```

The Kafka helper publishes to the start topic, while requests generated by the
running spider continue through its separate work topic. It accepts
`SCRAPY_CFFI_START_URL`, `SCRAPY_CFFI_KAFKA_INGRESS`, and a comma-separated
`SCRAPY_CFFI_KAFKA_BOOTSTRAP_SERVERS` value for single-broker or cluster checks.

## Local development infrastructure

`scrapy-cffi infra` continues to generate independent Docker services for local development. Production crawlers connect directly to independently deployed Redis/database/RabbitMQ/Kafka machines; the project container does not own those services.

See [0-start.md](./0-start.md#5infra) and `tests/test_broker/README.md` for single, Sentinel, and cluster verification.
